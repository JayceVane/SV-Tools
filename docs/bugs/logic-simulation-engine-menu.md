# logic-simulation-engine-menu

> **发现方式**：用户反馈自用工具链能单独使用，但标签页“仿真…”菜单中没有对应引擎。
> **定位耗时**：本轮定位，未单独计时。
> **修复位置**：`src/toolchains/simulation-engines.js`、`src/vivado/index.js`及本地入口注册。

## 症状

独立命令与状态栏已接入新工具链，统一仿真列表仍只有两个选项。原菜单根据内置二项数组显示，并将非Icarus选项一律派发给Vivado。

## 排查过程

1. 从标签页按钮的`svtools.simulate.pick`命令追踪，确认它仍使用Vivado组合层内的固定数组。
2. 本地入口只注册独立命令，未接入统一菜单；既有宿主测试直接调用独立命令，无法发现菜单接线遗漏。
3. 先补命令接线合同：公开两项/取消用例通过，扩展引擎用例在原实现失败：

```text
TypeError: h.api.registerSimulationEngine is not a function
```

## 根因

工具能力和统一入口分别维护，扩展命令的存在不代表按钮的候选列表与派发已接通。固定数组及二分派发还会把将来的第三个选项误送入已有工具。

## 修复

将菜单数据和执行回调放到会话级注册器。公共组合层只注册内置引擎，本地组装层另行注册额外引擎并持有注销句柄；通用模块不探测或导入本地工具链。

选择使用注册快照。取消、未知ID、注销或等待期间同ID重新注册都不运行任何工具；正常执行返回原回调结果，失败继续向调用方传播。公开入口保留两项，专用注册仍在公开构建排除范围内。

新增测试覆盖公开列表、注册/注销、真实命令派发和生命周期。宿主验收从实际统一菜单选择引擎并启动真实工具、加载VCD；不再以独立命令通过替代按钮入口验收。

## 教训

- 新增后端要覆盖用户实际使用的入口，分别检查独立命令与统一选择器。
- 选项与派发应来自同一注册来源，避免名称可见但执行分支缺失。
