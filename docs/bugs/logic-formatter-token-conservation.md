# logic-formatter-token-conservation

> **发现方式**：4.0发布审查，对字符守恒约束补真实编译器验证。
> **定位耗时**：本轮集中排查。
> **修复位置**：native/source_scan、format_guard、preprocess与范围对齐调用。

## 症状

`logic [8 + +1:0] a;` 被紧凑为 `logic [8++1:0] a;`。
`for(i=0;i<1;i++) a = a === 1;` 中的运算符被拆为 `== =`；`>>>` 变为 `>> >`。
原文Icarus编译退出0，原实现格式化产物编译退出2。

## 排查过程

字节序列守恒回归全部通过，但它忽略空白，无法识别两个token合并或一个token拆开。
先构造合法的二元加法后接一元加法表达式，再对for行长运算符逐项检查；14项旧NAPI回归全部失败。
仅在最终守卫回退虽然能阻止损坏，却会导致这类文件无法完成排版，因此还需修正范围紧凑和操作符规范化。

## 根因与修复

范围路径使用删除全部空白的规则，for路径的正则先匹配短运算符。两者都缺少最长匹配的词法边界。
共享扫描器现在流式返回完整token；紧凑只移除不会合并token的空白，for对完整运算符加空格。
最终守卫同时要求四种ASCII排版字符外的序列守恒、token一致、字符串/宏/转义标识符保护区保真。
不能证明安全时逐字返回原文。它是排版安全检查，不是完整SV解析或等价性证明。

## 验证与教训

21个既有golden保持原目标与幂等。真实Icarus对原文和格式化产物分别编译运行，输出完全一致：
`FORMAT_SEMANTICS_PASS width=10/10 case=1/1 shifts=-4/12 assign=16/6/-8/6`。
不要把字符守恒当成语义守恒；有语义的空白必须由词法边界决定。
