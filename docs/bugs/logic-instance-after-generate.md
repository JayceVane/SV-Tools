# logic-instance-after-generate

> **发现方式**：用户提供Aurora示例文件，报告例化模块无法对齐。
> **修复位置**：src/native/src/formatter/procedural.rs、codegen/align_code.rs。

## 症状

整文件格式化后支持模块的drp_clk_in仍未与其余端口对齐；单独取完整例化格式化却正常。对齐选区包含实例头或分组注释时原样返回。

## 排查过程

1. 对真实文件分别执行全文格式化、完整实例格式化、端口表选区和完整实例选区；只读记录原文件SHA256。全文出现两种左括号列位置，孤立实例只有一种，因此排除该连接行本身无法解析。
2. 分离模块头、属性、声明与generate正文。模块头、属性和声明均不会触发；generate内单个always也正常，但always→assign→含if的always组合会让后续实例被跳过。使用公开的合成代码固定最小复现，没有将供应商源码加入回归仓库。
3. 过程块的完成判定仅接受Code/Module/Interface，漏掉Generate。多个过程之间状态变化后，最后always无法在generate上下文提交，其状态残留到后续模块实例。
4. 选区是独立问题：分类只看首条非空行，把分组注释和实例头落入赋值分支；该分支使用Rust regex不支持的前瞻，panic被字符守卫捕获后回退原文。先新增四个失败的Rust回归，再修复并补齐NAPI回归。

## 修复与边界

过程块允许在Generate上下文中正常提交；不扩大到不合法的过程作用域。选区类型以共享词法掩码中的第一段代码决定，完整实例调用现有普通段格式化入口，端口表沿用选区括号起始列对齐，声明和赋值各用自身布局。赋值通过共享原文捕获读取左右区间，不再用前瞻，也不把注释/字符串中的等号作为运算符。

字符守卫没有放宽：仅空格、Tab、CR、LF允许改变，其余字符的数量和值及顺序必须相同。原始宏、字符串和注释仍由词法保护。完整实例选区使用该入口的默认布局与指定tabSize；它没有新增完整SV语法能力。

## 验证

Rust四个新增回归与NAPI四个回归覆盖generate后实例、完整实例选区、注释前缀端口表和选区赋值；另含LF/CRLF、TAB、既有GNU布局、仅缩进及禁用端口对齐开关。真实用户文件只读验证支持模块36端口的左/右括号分别同列，全文幂等、非排版字符序列相同、注释保真和磁盘SHA256不变。详细版本数据见../V4_1_ALPHA8.md。

## 经验

局部布局正常、全文失败时应优先检查上一个构造的提交状态。安全回退能保护文本，但不能替代“结果确实发生了目标对齐”的断言。
