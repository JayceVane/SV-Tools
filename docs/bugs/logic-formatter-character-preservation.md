# logic-formatter-character-preservation

> **发现方式**：用户要求任意乱码输入只允许改变普通空格、CR、LF、Tab；旧CLI隔离复现失效。
> **修复位置**：`src/native/src/format_guard.rs`、`bindings.rs`、`src/editor/format-safety.js`及布局入口。

## 症状

旧CLI对 `\u000b\u000c\u00a0\u3000\ufeff\ufffd乱码🚀\n` 正常退出0，但删除了
VT、FF、NBSP、全角空格。`--one-decl-per-line` 对 `logic [7:0] a, b;` 重复类型，
把逗号改为分号。两者均违反忽略且仅忽略四种ASCII布局字符后的原文序列相等条件。

## 排查过程

1. 先用CLI子进程隔离未知输入，比较过滤 `[\x20\t\r\n]` 后的正文，确认是实际
   字符丢失和改写；不能用 `\s` 比较，否则损坏的Unicode空白也被测试过滤掉。
2. 全文和普通段入口会经历预处理、主布局、对齐、空行、保护区拼接；逐个修补特定
   语法无法约束全部乱码。因此在公开布局边界统一校验候选，并注入错误候选/panic验证回退。
3. 检查本机napi 2.16.17：普通 `String` 读取使用 `napi_get_value_string_utf8`，
   无法追回JS原有孤立代理项。改为 `JsString` 严格读取UTF-16，失败时返回原句柄。
4. 编辑器用故障native替身注入删除、增加、换字、乱序、错误类型和有损替换，确认
   在全文及选区替换之前仍能拒绝；正常排版结果可以提交。
5. 真实native和CLI的新语料两轮守恒/幂等均通过。新验收曾怀疑声明对齐正则有实际
   换行；源文件复核与正常logic对齐实测排除了这一显示误判，没有为此修改算法。

## 根因

原先只有各语法分支的局部保护，没有整段输出的提交条件。宽泛Unicode空白处理、
声明拆分等结构改写和宿主的UTF-16→UTF-8有损转换发生在不同层；只比较token、
去掉全部 `\s` 或只检查Rust收到的文本，均不能证明编辑器原文未损坏。

## 修复与取舍

Rust按UTF-8字节迭代、编辑器按UTF-16码元迭代，只忽略ASCII四字符，线性比较且不
构建过滤后大字符串。校验失败或Rust布局异常时返回对应入口原文并输出不含源码的
诊断；原文优先于行尾归一和声明拆分。严格UTF-16边界保留无法转换的JS字符串。
CLI已有严格UTF-8读取，回归确认读取失败不会覆盖输入或既有输出。

选区对齐的旧赋值分支仍使用Rust regex不支持的lookahead；未知输入进入该分支会
触发布局panic。现在捕获后保留原文，不会退出宿主；赋值对齐算法的修复留作独立维护项。
Rust默认panic hook的诊断仍可出现在日志中，守卫不修改全局hook。

## 教训

- 字符保全必须比较原始序列和值与次数，不能只比较排序后的集合或词法token。
- 宿主转换之前的原文也属于保护范围；编码问题不能交给已收到替代字符的核心补救。
- 用正常排版仍生效、错误候选被拒绝、真实二进制不写坏文件三类证据共同验收。
