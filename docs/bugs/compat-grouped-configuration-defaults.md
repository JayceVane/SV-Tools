# compat-grouped-configuration-defaults

> **发现方式**：用户反馈自用包在Qoder中无法格式化axis_if.sv
> **定位耗时**：一次会话
> **修复位置**：src/configuration.js、src/editor/formatting.js
> **修复提交**：见本文件的Git历史

## 症状

自用包激活、仿真及查看器可用，执行格式化后文本不变。直接调用该包的配置模块报错：

```text
TypeError: Cannot read properties of undefined (reading 'svtools.indentStyle')
    at readOption (.../src/configuration.js:8:39)
```

修复前解包local.5在VS Code与Qoder中都未通过真实格式化验收的首条断言。

## 排查过程

1. 只读核对用户文件、Qoder已安装包与工程设置；未修改原工程，也没有通过关闭字符守卫绕过问题。
2. 同一文件使用公开清单默认值直接调用现有NAPI，格式化有变化、字符保全且幂等；排除该样本必然触发原生回退的假设。
3. 比较两种包的配置读取：公开包返回16个格式化字段，自用包在读取首个默认值时抛出上述异常。
4. 追踪清单组装后发现配置分组已从对象变为数组；此前宿主验收只覆盖自用仿真流程，核心格式化宿主验收只运行在公开清单上。

## 根因

配置贡献支持单对象及分组数组两种结构。旧代码直接读取
`contributes.configuration.properties`，分组后此属性为undefined。
`config.get(name, properties[key].default)`会先计算fallback，即使实际设置存在也会报错。
格式化的配置组装又位于try之外，未显示预期的错误提示。例化和测试台生成复用同一配置模块，也受影响。

## 修复

在配置模块入口把单对象规范为数组，再合并各分组的properties，继续由原清单提供默认值；不修改格式化规则或NAPI。
把格式化配置和文本读取纳入原有异常处理，配置失败也明确提示并返回null，不提交编辑。
新增先失败后通过的回归：单组/多组的三类选项一致，显式false、0、空字符串保持，全文及选区的配置异常可见。

自用构建在组装后的staging上验证真实配置、NAPI格式化、字符保全、幂等、例化和测试台生成；
真实自用宿主先复用公开核心验收，再检查用户样本副本的全文、选区和保存格式化，最后运行仿真流程。
用户文件只读，样本不加入公开golden或安装包。

验收结果：完整golden44/44、Node672通过/11可选跳过、电路170/170；最终local.6解包包在
VS Code1.143与Qoder API1.106.3各18/18，包含用户样本副本全文、选区、保存时格式化，
以及原有自用仿真操作。原文件SHA256前后保持。

## 教训

1. 读取编辑器贡献清单时应覆盖合法的全部结构，不能把当前公开清单的布局当作运行合同。
2. 组装后的包必须验证已有核心功能；扩展激活成功和新增工具可用都不能证明格式化可用。
3. 默认值表达式也可能抛错，应在提交编辑前统一处理配置和原生调用异常。
