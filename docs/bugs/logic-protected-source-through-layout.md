# logic-protected-source-through-layout

> **发现方式**：4.0 重构后的完整管线审查与新增合同测试，原有 golden 未覆盖这些输入。
> **定位耗时**：跨两次会话。
> **修复位置**：`src/native/src/source_scan.rs`、`align/{assign,decl}.rs`、`blank_rules.rs`。

## 症状

以下为本机只读加载 3.5.0-beta10 和最终 4.0.0-alpha1 native 模块得到的实际输出片段：

```systemverilog
// 输入
string short = "a;b";
// 3.x 输出
string short = "a; b";
// 4.0 输出
string short = "a;b";
```

多行三元赋值中的 `f("a  b") +` 曾输出为 `f("a b") +`。块注释内的
` a=1;`、` longer=2;` 曾被重新对齐成 `a      = 1;`、`longer = 2;`。
宏续行里的假 `begin` 还会影响后续真实声明的空行，造成二次格式化变化。

## 排查过程

1. 第一轮发现预处理按 UTF-8 字节转字符、注释关键词参与 `begin` 合并。
   引入 lossless scanner 和保护 token 后，这些问题通过测试，原有 golden 也全部通过。
2. 完整管线追加字符串分号、连续空格、块注释内假赋值、宏续行案例，仍发现内容变化。
   单独调用对齐器可复现，说明问题不止在主调度：后续 pass 重新识别了受保护文本。
3. 简单把保护区替换为空格仍不安全：正则的 `\s*` 会吞掉整个字符串占位，
   字段边界不能再对应完整原文；跨行注释的关闭前缀也会被当作缩进删除。
4. 掩码改用等长非空白字面量占位、保护行首哨兵，并由 captures 适配器返回原文切片。
   赋值第二遍对齐也改用完整块掩码；逐行扫描空行规则改为全文扫描，保留宏上下文。

## 根因

词法保护是一条贯穿所有 pass 的合同。主循环识别 `Protected` 并不能保证后处理安全；
声明正则的 `[^;]+`、赋值续行的空格压缩和空行 pass 的关键词识别都曾在原始文本上
重新解释字面量、注释和宏。逐行重建扫描状态还会丢失跨行保护区的上下文。

## 修复

```rust
// 原来：正则直接识别原文。
re.captures(line)
// 现在：仅识别掩码，字段内容仍来自原文。
source_scan::captures(re, line, masked_line)
```

掩码保留字节长度和换行位置；captured 范围检查长度与 UTF-8 边界后才映射原文。
只对 Code 区压缩空白，保留转义标识符的终止空白。以全文保护区区间计算空行状态，
宏正文里的关键字不进入结构栈。额外扫描是正确性成本，固定正则仍复用惰性缓存。

最终 Rust 106/106、golden 36/36、JavaScript 合同 78/78 通过。
新增案例既检查保护区原文和幂等性，也检查相邻真实代码的对齐，防止通过跳过布局掩盖问题。

## 教训

1. 发现源码内容被改变时，逐个检查所有后处理 pass，而不只检查 tokenizer。
2. 掩码用于结构事实，原文用于输出；正则字段必须验证原文字节边界。
3. 验证保护区时同时验证周边代码仍正常格式化，跨行状态应从完整文本获取。
