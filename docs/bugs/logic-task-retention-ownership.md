# logic-task-retention-ownership

> **发现方式**：用户要求审查新增的任务目录封顶逻辑，隔离复现确认。
> **定位范围**：目录异步扫描、跨宿主所有权与电路快照延迟读取。
> **修复位置**：`src/toolchains/task-retention.js`、`job.js`、`src/circuit/index.js`。
> **修复提交**：`84bd364bc449c5d5546824361129a477aaec64f2`。

## 症状

任务仍为`isCurrent: true`，其`input.sv`却已经不存在；两个独立管理器也可复现。
打开未保存正文的电路后继续生成其它电路，旧图稍后请求源码位置时报错，实际前缀为：

```text
ENOENT: no such file or directory, open
```

原有46项工具链和源码定位测试全部通过，不能证明目录生命周期安全。
缺失路径指向已被淘汰的`source-*`目录内的`lane.sv`快照。

## 排查过程

1. 挂起`readdir`，在旧清理捕获保护集合后启动3个新任务。keep=1时有2个活动输入被删，
   排除“目录只会在工具结束后被扫描”的假设。
2. 用另一个Node进程持有活动目录；主进程完成数次任务后，原实现删除了子进程目录。
   因此仅在删除前重读当前管理器的集合，仍不足以保护其它窗口。
3. 对真实命令入口、Worker和ELK执行脏正文快照测试。原实现后续生成会删除旧快照；
   修复后旧图的按需声明定位保持有效，刷新和关闭才交还占用。
4. 同时运行4次淘汰，4个实际过期目录被重复报告为15次删除，Windows偶发EPERM。
   同进程按父目录/类型串行后，每个路径只报告一次。

## 根因

“不在本管理器此刻的活动集合中”不能证明目录已无人使用；任务结束也不代表产物的
所有消费者结束。保护集合既缺少其它宿主的事实，也丢失了电路面板的资源所有权。

## 修复

新目录默认不可淘汰。任务和面板分别持有幂等可释放的占用，最后一次释放才写入
`.svtools-task-complete.json`，标记绑定当前目录名。完成状态不可逆，目录不能再借用。
淘汰仅接受有效完成标记，因而不需要猜测PID、超时或另一个宿主的活动集合。
同一父目录/类型的淘汰在进程内串行；其它宿主已删除的目标不重复报告失败。

取舍是旧版本及异常退出留下的未标记目录需要在停止相关工具后手动清理；自动清理
优先避免破坏在途任务。keep=0仍发布完成状态，但不启动淘汰。

## 教训

1. 自动删除应基于不可逆的完成事实，而不是某个时刻的缺席信息。
2. 产物的寿命由最后一个消费者决定，不能直接绑定生产任务结束。
3. 并发、跨进程与延迟消费者需要单独回归，串行快乐路径不能覆盖所有权竞态。
