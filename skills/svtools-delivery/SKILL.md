# RTL 设计、验证与交付

适用：新模块、功能变更、缺陷修复和模块验证报告。纯格式化或只读查询不要求建立完整验证项目。细则与交付清单见 [references/delivery.md](references/delivery.md)；本页是要点与硬规则。

## 硬规则（违反即交付未完成）

1. **需求先行**：需求表同时写验证方法和判定条件，避免实现后为已有行为反写规格。未指定且影响功能的条件（复位期间输出、满/空同时读写、跨域复位先后、背压、溢出、参数退化值）须明确为假设或向用户确认，不能静默决定。
2. **职责分离**：设计侧交付 RTL/设计说明/假设，不自行宣布完整验证通过；验证侧依据同一规格建立**独立**参考模型/断言/TB，不为使测试通过修改 DUT 或放宽期望。设计侧的推理可作线索，不能代替验证侧的独立期望。小修改可单 Agent 分阶段完成，但须披露独立性限制；CDC、多时钟、复杂协议、多模块重构优先独立验证子 Agent（是否启动由客户端能力与授权决定）。
3. **模块验证报告必含 ΔCycle 排查**：用 `wave glitches`（svtools-waveform 技能）检查相关信号窗口并逐项处置（预期组合收敛 / 缺陷 / 证据不足）；没有波形、信号未 dump、命令不可用或扫描不完整时，报告仍须有这一项并标未执行/受阻及原因。命中不自动判缺陷；零命中只能表述为"该运行、已检查信号和窗口内未发现文件记录的同刻瞬态"，不能声称电路无毛刺或已完成 CDC/模拟时序验证。此项要求执行和判断，不要求所有组合瞬态数量为零。
4. **证据可追溯**：任一通过结论能追到需求 ID、用例 ID、检查规则、实际运行命令与日志/波形身份（波形 SHA-256 只证明文件身份；`evidence.sourceBinding=unverified` 必须由实际仿真命令、输入快照和运行产物建立关联，不能自行改成"已绑定"）。Git 提交号只能辅助识别。
5. **输入变化即失效**：源码/TB/约束/参数等输入变化后重跑受影响检查；旧证据不自动继承到新实现。

## 最小交付物

| 产物 | 必需内容 |
| --- | --- |
| `requirements.md` | 需求 ID、可观察行为、边界、假设、验收条件 |
| `design.md` | 接口/参数、时钟复位、数据通路和控制、延迟、取舍、已知限制；复杂结构附 `design report` 图表清单 |
| `verification_plan.md` | 需求→用例→独立期望→检查方法；种子/参数矩阵；需检查的时钟、复位、valid/ready、使能和标志信号及窗口 |
| `verification_report.md` | 每项判定、实际运行命令、版本、日志、失败复现/修复复验、**ΔCycle 排查**、未验证项与最终结论 |
| `verification-evidence.json` | 源码、TB/参考模型/约束及波形身份；工具版本、top、参数、种子、命令/退出状态、产物路径和 SHA-256；需求/用例/检查结果索引 |

原始产物可放 `.svtools/verification/<module>/<run-id>/`。已有等价文件时补充，不另建重复体系。判定使用 `passed/failed/blocked/not_run/not_applicable`（后者须有适用性依据）；必需检查有失败、未执行、受阻、来源不明或未处置命中时交付为未完成并给出下一步。

## M5 联合验收

先在一个简单同步模块验证交付链，再用参数化 FIFO/多时钟设计验证复位、握手和瞬态处置，最后进入真实 Vivado 工程与插件/CLI 对照。通过条件是需求、独立检查、运行身份、图表和报告互相可追溯，且注入缺陷能被发现、修复后能按原规则复验。MCP 和自动多 Agent 编排不作为这套流程的前提。完整分批计划见 [references/delivery.md](references/delivery.md) 与 `docs/V4_2_PLAN.md`。
