# RTL 设计、验证与交付

适用于新模块、功能变更、缺陷修复和模块验证报告。纯格式化或只读查询不要求建立完整验证项目。沿用用户工程已有的目录与报告格式；以下文件名是默认建议。

## 先确定交付对象

为需求分配稳定 ID，明确端口/虚拟接口、参数合法范围、时钟域、复位时序、数据格式、延迟/吞吐、握手和异常行为。未指定且影响功能的条件须明确为假设或向用户确认，不能静默决定。例如：复位期间输出、满/空同时读写、跨域复位先后、背压、溢出与参数退化值。

需求表同时写验证方法和判定条件，避免实现后为已有行为反写规格。正常、边界、异常、复位恢复及必要的并发场景按模块实际风险选择。区分功能检查、结构检查、综合/实现指标、CDC/时序与记录级瞬态诊断；一种证据不能替代另一种。

## 职责与交接

| 职责 | 输入 | 负责的产出 | 判断边界 |
|---|---|---|---|
| 设计 | 已确认需求、接口与约束 | RTL、设计说明、接口表/架构图、实现假设、变更清单 | 不自行宣布完整验证通过 |
| 验证 | 同一规格、接口、参数、时钟/复位约束、待测版本 | 验证计划、独立参考模型/断言/TB、复现与回归、验证报告和证据索引 | 不为使测试通过修改 DUT 或放宽期望 |
| 主 Agent / 集成 | 两侧产出与冲突 | 需求追踪表、问题裁决、合入版本、最终交付摘要 | 依据复现与证据裁决，不用多数意见替代事实 |

独立验证先依据规格建立检查点，再读取实现定位问题。验证交接提供文件/实例/top、RTL 源码哈希、需求 ID、工具/运行方式、已有失败与已知限制；不要只给设计侧的“已通过”结论。设计侧的推理可作为线索，不能代替验证侧的独立期望。

小修改可由一个 Agent 分阶段完成并说明独立性限制。CDC、多时钟、复杂协议、多模块重构、较大验证任务优先分配独立验证子 Agent；是否真的启动由调用端能力和当前授权决定，Skill 不提供或假设专用编排服务。没有子 Agent 时继续单 Agent 流程，不伪称独立复审。

并行时设计与验证使用分离的工作树或明确文件归属；验证侧可改 TB/断言/参考模型，DUT 问题交回设计侧。共享 Vivado 工程和仿真输出不可同时写入。交接期间 RTL 改变则重新绑定版本，不能把旧结果签给新实现。

## 最小交付物

| 产物 | 必需内容 |
|---|---|
| `requirements.md` | 需求 ID、可观察行为、边界、假设、验收条件 |
| `design.md` | 接口/参数、时钟复位、数据通路和控制、延迟、取舍、已知限制；复杂结构附 `design report` 图表清单 |
| `verification_plan.md` | 需求→用例→独立期望→检查方法；种子/参数矩阵；需检查的时钟、复位、valid/ready、使能和标志信号及窗口 |
| `verification_report.md` | 每项判定、实际运行命令、版本、日志、失败复现/修复复验、ΔCycle 排查、未验证项与最终结论 |
| `verification-evidence.json` | 源码、TB/参考模型/约束及波形身份；工具版本、top、参数、种子、命令/退出状态、产物路径和 SHA-256；需求/用例/检查结果索引 |

原始产物可放 `.svtools/verification/<module>/<run-id>/`，交付说明引用它们；需要随项目交付的文档遵循用户目录。已有等价文件时补充，不另建重复体系。这些是交付约定，当前没有名为 `verification report` 的 CLI，不能编造命令。

证据索引至少能从一个通过结论追到需求 ID、用例 ID、检查规则、实际运行和日志/波形。Git 提交号只能辅助识别，不能替代源码、TB、约束、参数/宏和工具版本的身份。波形 SHA-256 只证明文件身份；`wave glitches.evidence.sourceBinding=unverified` 必须由实际仿真命令、输入快照和运行产物建立关联，不能自行改成“已绑定”。有真实覆盖率报告才引用其数字，不推测未提供的覆盖率。

## 模块验证报告必须包含 ΔCycle 排查

1. 在验证计划中选定相关信号及范围：优先时钟、异步复位、握手/写读使能、满空等控制输出及其关键组合条件。说明 DUT 实例、实际 dump 的信号、复位/工作/恢复窗口；无法自动完整枚举时列出已查和未查范围。
2. 使用 `wave glitches --file <vcd|fst> --signals <完整路径,...> [--from ... --to ...]` 保存 JSON 结果。该查询读同刻的原始记录，普通 `wave values/changes/edges/sample` 取终值，不能用后者代替这一步。
3. `series[].next` 是下一页闭区间 `--from`，按该信号逐页继续，直到 `complete=true`。预算不足/截断时不能把 `matched=0` 解释为无问题；`stopReason=query-decode-budget` 的整组超限不能靠反复相同查询解决，需要缩小所选对象或说明未覆盖。`sequenceTruncated=true` 时记录证据限制；需要完整序列可提高 `--max-values`（最多 256）或进一步定位。
4. 逐项处置初始化、回跳和终值变化活动。结合接口契约、采样沿、复位、驱动关系与上下文说明：预期组合收敛、缺陷、或证据不足。命中不自动判缺陷，也不以“最终值正确”排除对时钟/复位/异步接收端的风险。
5. 修复后用相同信号、参数、种子和检查规则重新运行；保留前后证据与解释。实际时间宽度的窄脉冲另用 `changes/edges` 和时刻差检查，不能从同刻记录序号推导物理脉宽。

报告必须写出 `recordingCompleteness=unknown` 的含义：文件只包含仿真器实际记录的变化，可能已经折叠中间值；不能恢复真实调度区/全局 delta 编号。特别是转换/压缩或仿真器记录方式变化后，应优先保留原始取证波形。无命中只能表述为“该运行、已检查信号和窗口内，未发现文件记录的同刻瞬态”，不能声称电路无毛刺或已完成 CDC/模拟时序验证。

没有波形、信号未 dump、命令不可用或扫描未完成时，报告仍须有这一项，标为未执行/受阻并给原因；不得宣称完整验证通过。此项要求执行和处置，不要求所有组合网络的瞬态数量为零。

## 判定与复验

每个检查使用 `passed` / `failed` / `blocked` / `not_run` / `not_applicable`，后者须有适用性依据。查询退出 0 只表示取数成功；`semantics.acceptance=false` 是工具的固有边界。验证结论由规格、完整扫描、已处置异常及其他必需检查共同形成。

必需检查有失败、未执行、受阻、来源不明或未处置命中时，交付为未完成并给出下一步。缺工具与空报告不能记零错误通过。源码/TB/约束/参数等输入变化后重跑受影响检查；Vivado 报告同时核对 stale 和运行阶段。

最终报告回答：实现了哪些需求、用什么独立规则验证、哪份输入产生哪次结果、ΔCycle 命中如何处置、哪些结论仍无证据。设计与验证意见冲突时提交最小反例和原始证据；规格本身矛盾则回到需求决策，不通过修改测试隐藏冲突。

## M5 联合验收

先在一个简单同步模块验证交付链，再用参数化 FIFO/多时钟设计验证复位、握手和瞬态处置，最后进入真实 Vivado 工程与插件/CLI 对照。通过条件是需求、独立检查、运行身份、图表和报告互相可追溯，且注入缺陷能被发现、修复后能按原规则复验。MCP 和自动多 Agent 编排不作为这套流程的前提。
